Theory

1. Why fast hashes fail for passwords

A cryptographic hash such as SHA-256 is designed to be fast: a modern CPU computes billions of SHA-256 digests per second, and a GPU billions more. When a password database is stolen, the attacker does not need to break the hash function — they simply guess passwords, hash each guess, and compare. Every additional billion guesses per second is free speed for the attacker.

Attacks against stolen password files are offline: the defender cannot rate-limit them. The only defence is to make each single guess expensive. That is the job of a password hashing scheme / key derivation function (KDF).

MD5 / SHA-1 / SHA-256 (plain)1992–2001nonenone — attacker hashes at full CPU/GPU speed

2. The Argon2 design (RFC 9106)

Argon2 was designed by Alex Biryukov, Daniel Dinu and Dmitry Khovratovich (University of Luxembourg) and won the Password Hashing Competition in 2015. It is standardised as RFC 9106. Its central idea is memory hardness: the function fills a large internal memory array of m blocks (each block is 1024 bytes = 8 × 128-byte "rows"), and every new block depends on previously written blocks. An attacker who wants to compute many hashes in parallel must therefore also buy the memory for each — memory, unlike arithmetic logic, is not cheap to scale on a GPU/ASIC die.

2.1 Inputs

  • Message P — the password (bytes).
  • Nonce S — a 16-byte salt, unique per password, stored alongside the hash.
  • Secret key K (optional) — a "pepper", e.g. held in a config file not in the DB.
  • Associated data X (optional) and tag length T.
  • Cost parameters: memory size m (in KiB), number of iterations/passes t ≥ 1, parallelism/lanes p ≤ 4.
  • Type: Argon2d, Argon2i or Argon2id.

2.2 Internal structure

  1. Initial hash H₀. All inputs (password, salt, parameters) are hashed into a 64-byte initial hash H₀ with BLAKE2b. H₀ determines the first two blocks of every lane.
  2. Memory allocation. Allocate m′ = 4·p·⌊m/(4p)⌋ blocks — a multiple of 4·p so every lane gets an equal slice. In this lab the visualiser shows this array directly.
  3. Fill pass. For each pass r = 1…t, and each lane, each slice, each segment: compute new blocks. Block i is computed from the reference block J₁, the previous block, and (from the second slice onward) a second reference J₂. The compression function G (built on BLAKE2b rounds mixed with a permutation-based mixing layer) combines them.
  4. Addressing — the three types:
    • Argon2d — reference blocks are chosen from the data already in memory (data-dependent). Fastest against GPUs and side-channel-unsafe. Best for non-password uses and cryptocurrencies.
    • Argon2i — reference positions come from a pseudo-random address generator independent of memory contents (data-independent). Side-channel safe, but needs more passes for full memory coverage.
    • Argon2id — hybrid: the first half-pass uses Argon2i addressing, the rest Argon2d. Gets side-channel resistance and GPU resistance. This is the variant recommended for password storage.
  5. Finalisation. XOR the last block of each lane, hash with BLAKE2b to produce the T-byte tag.

2.3 Memory visualisation

In the Simulation, the "Memory Grid" tab animates this fill process on a small array: grey cells are unwritten blocks, blue cells are filled (darker for later passes), orange is the block being computed, and yellow are the reference blocks feeding it. For Argon2i/id you can watch the address sequence jump pseudo-randomly; for Argon2d the references depend on the data being written.

3. The PHC string format

Argon2 output is conventionally stored as a self-describing PHC string that embeds the algorithm, version, parameters, salt and tag — so hashes can be verified years later and parameters can be upgraded transparently:

$argon2id$v=19$m=19456,t=2,p=1$<base64 salt>$<base64 tag>
   │        │    │        │              │
   │        │    │        │              └─ 32-byte tag (b64, no padding)
   │        │    │        └─ 16-byte salt (b64, no padding)
   │        │    └─ memory KiB, iterations, parallelism
   │        └─ version 1.3 (0x13)
   └─ variant (argon2d / argon2i / argon2id)
Reading example: $argon2id$v=19$m=19456,t=2,p=1$… means Argon2id, version 1.3, 19 MiB of memory, 2 passes, 1 lane — the current OWASP-recommended minimum for interactive login (roughly 19 MiB, t=2, p=1).

4. Choosing cost parameters

Three knobs trade security against user-perceived latency:

ParameterMeaningEffect of increasing it
m (memory cost)RAM used, in KiBRaises the hardware cost of the attacker linearly — the strongest knob
t (time cost)Passes over memoryRaises CPU time (and attacker's energy cost); also improves Argon2i coverage
p (parallelism)Lanes / threadsUses multiple cores; with fixed m and t it slightly weakens per-guess cost, but enables m to be raised for the same wall time

Practical recipe (RFC 9106 §4 and OWASP): pick the maximum m your server can afford (OWASP: ≥ 19 MiB), then choose t so that one hash takes the target time (≈ 0.5–1 s for interactive login). Use p = 4 only if the server has idle cores. Measure — never trust defaults. The Simulation's Benchmark tab does exactly this measurement in your browser.

5. Salting & rainbow tables

A rainbow table is a precomputed dictionary hash → password. It works only when every user's hash was computed the same way — i.e. unsalted. A salt is a random value mixed into the input; because it is unique per password, two users with the password hunter2 get entirely different digests, and a table built for one salt is useless for another. Salting does not slow a targeted attack on one account (that is what memory-hardness is for) — it defeats amortised attacks across many accounts. The Simulation's Salt & Rainbow tab demonstrates this.

6. Security analysis

  • Tradeoff attacks: an attacker can reduce memory and pay with more computation (e.g. 1/3 memory ≈ 3× more time for Argon2d/i at moderate depth). This is the reason to keep raising m over the years rather than relying on t.
  • Side channels: Argon2d leaks reference positions through cache timing — use Argon2id for passwords.
  • GPU resistance: at m = 1 GiB a GPU with ~10 GB of RAM can run only ~10 guesses concurrently, versus millions of SHA-256s — this is the economic core of memory hardness.
  • Known cryptanalysis: reduced-round BLAKE2b-based G has known distinguishers, but the full function has no practical attacks; RFC 9106 recommends ≥ 3 passes when using Argon2i, and Argon2id with t ≥ 2 otherwise.

7. Practical applications

  • Password storage in web applications (the primary use; format above is what frameworks like Django, PHP's password_hash(), and libsodium emit).
  • Key derivation for disk/volume encryption and for deriving AES keys from passphrases.
  • Proof-of-work and cryptocurrency (Argon2d chosen by some chains for its time–memory tradeoff characteristics).
  • Entity authentication — hardening of password-based login and of PAKE-style protocols.
